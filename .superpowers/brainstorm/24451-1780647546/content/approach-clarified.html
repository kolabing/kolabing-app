Answers to your three questions

Before picking an approach — here's what the codebase actually shows.

A — Dark as default ✓ Easy

The ThemeService already defaults to ThemeMode.system, and main.dart hardcodes ThemeMode.light (the provider is wired but ignored). Flipping to dark-first means: default = ThemeMode.dark, light is an opt-in in Settings. No structural change needed.

B — Which files already use colorScheme?

Of the 35 files that call Theme.of(context), almost all of them only check .brightness (to branch between light/dark manually). Only 3 lines in the entire codebase actually read a colorScheme slot (.outline and a copyWith). Everything else is hardcoded KolabingColors.xxx.

Conclusion: Approach B gives almost no free rides. You'd still have to migrate each widget manually — it's effectively the same effort as C, but less clean.

C — Exact migration process for a separate branch

Yes — here's the exact recipe:

  1. git checkout -b feat/dark-theme-full-migration
  2. Define KolabingColorTokens as a ThemeExtension with both light + night sets
  3. Run a codemod script I write: replaces every KolabingColors.xxx in 144 files with context.colors.xxx (or ref.colors.xxx in Riverpod widgets)
  4. Fix the ~20 files where static context is unavailable (non-widget classes, factories, etc.) — those stay as KolabingColors.xxx as fallbacks
  5. Run flutter analyze + visual smoke test
  6. Open PR → merge to main

Estimated scope: ~4–6 hours of work, mostly automated. The codemod handles 90%+.

Recommendation

Given that dark is the primary theme and you're open to the full migration — Approach C is the right call. Do it now (not deferred): define the extension, write the codemod, migrate all 144 files, wire the provider in main.dart, and implement all 4 night screens. One clean branch, one PR.

Approach A would leave 140 screens broken in dark mode — since dark is now the default, that's not acceptable.
