How should Night Mode tokens be delivered to widgets?

144 files currently hardcode KolabingColors.xxx. The night mode spec requires these resolve differently at runtime. Three approaches:

A

BuildContext Extension — context.colors.ink

Add a KolabingNightColors class (all night tokens) and a context.colors extension that returns the right set based on Theme.of(context).brightness. Migrate only the 4 target screens to use context.colors.xxx. All 140 other files stay untouched and keep rendering in light mode regardless of system preference.

Pros

  • Zero risk to existing screens
  • Clean, self-contained night set
  • Easy to extend later

Cons

  • Two color APIs coexist (KolabingColors vs context.colors)
  • Non-target screens stay light even in night mode
B

ColorScheme Mapping — Flutter dark ThemeData

Fill out KolabingTheme.darkTheme with a proper ColorScheme.dark using the night tokens. Widgets that use Theme.of(context).colorScheme.xxx get night mode automatically. Widgets that still hardcode KolabingColors.xxx need to be migrated one by one.

Pros

  • Idiomatic Flutter M3 pattern
  • Chips, buttons, inputs inherit dark theme automatically

Cons

  • Many night tokens don't map cleanly to ColorScheme slots
  • Still need per-widget migration for custom colors (XP card, mission tiles, etc.)
C

InheritedWidget Theme Extension — fully custom token bag

Register a KolabingColorExtension as a Flutter ThemeExtension. Define it for both light and dark in ThemeData. All widgets call Theme.of(context).extension<KolabingColorExtension>()!.ink. Full migration of all 144 files required.

Pros

  • Single source of truth for both themes
  • Lerps automatically on theme transitions
  • Most architecturally pure

Cons

  • Requires migrating all 144 files
  • Highest upfront effort
  • Verbose call site
